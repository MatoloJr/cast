Cast Display

Cast your screen to Chromecast and Google TV from GNOME's Quick Settings. Mirror a screen or extend your desktop onto the television, send the audio with it and drive several receivers from a single encode.

[warn] Read this before you trust it. Everything described here has been exercised end to end on Ubuntu 26.04 / GNOME Shell 50.1, with the development harness and with real display and portal behaviour. What has not been confirmed is a picture on a real television: the stream format this version sends has never been seen playing on hardware. One receiver has been tested and it refused every other format tried. Nothing on this page is described as working on a TV that has not been seen working on one.

What it does

MirrorShare an existing screen. The desktop portal asks which one.
ExtendCreate a virtual monitor for the television, so it becomes a second desktop you can drag windows onto. It appears in Settings → Displays.
TV onlyExtend, then switch this computer's screens off — with a 15 second “keep these settings?” timer that reverts itself if you do not answer.
Several receiversSelect more than one, or add one mid-stream without re-prompting and without interrupting the others.
AudioSend what the computer is playing, with an A/V offset control and an optional “mute this computer while casting”.
MiracastOne row that opens GNOME Network Displays, or offers to install it. This extension implements no Miracast of its own.

While casting, a cast icon appears in the top bar with the receiver count and notification banners can be hidden automatically.

Requirements

  • GNOME Shell 45–50, on Wayland. Developed and verified on 50.1.
  • PipeWire and a working xdg-desktop-portal with the ScreenCast interface. Portal version 4+ avoids a permission prompt on every connect; Extend additionally needs the portal to offer the VIRTUAL source type.
  • An H.264 encoder GStreamer can use — VA-API (vah264enc) if you have it, otherwise x264enc.
  • Python 3.9+ with PyGObject and ffmpeg for the diagnostics.

Install

git clone https://github.com/MatoloJr/cast
cd cast
./install.sh

Then log out and back in. On Wayland the Shell cannot reload itself, so the tile will not appear until the session restarts. No reboot is needed and the helper starts immediately. On X11 press Alt+F2, type r and press Enter instead.

Using it

Quick Settings → Cast Display.

  • The chevron opens a dialog in the middle of the screen. Tick one or more displays and press Connect.
  • The tile itself is a switch. While a cast is running it stops it. Otherwise it casts straight back to the receivers you last used and only falls back to opening the dialog when there is nothing to go back to.
  • Super+K opens the dialog from anywhere, without going through Quick Settings.
  • Everything else lives in the preferences: mode, resolution, frame rate, bitrate, audio and its offset, the port range, the shortcut and a Forget button that clears the receivers the tile resumes to.

The picker used to be a Quick Settings dropdown. A dropdown is anchored under its tile, has no scroll view and no height bound, so on a laptop panel its lower half ran off the bottom of the screen with no way to reach it. The dialog measures itself against the monitor's work area and scrolls only the device list. On a 1366×768 panel with twelve receivers listed, the list is capped at 393 px and the whole dialog comes to 697 px inside a 736 px work area.

Uninstall

cd cast
./install.sh --uninstall

It removes, in this order:

  • disables the extension (gnome-extensions disable)
  • stops and disables cast-helper.service, then deletes the unit file
  • deletes the D-Bus service file org.cast.tools.Cast1.service
  • deletes ~/.local/share/cast-display/ — helper, virtualenv and all
  • deletes $XDG_RUNTIME_DIR/cast-display/
  • deletes ~/.local/state/cast-display/, including the saved screen-share permission, so the portal will ask again after a reinstall
  • removes the extension symlink and runs systemctl --user daemon-reload

Two things it will not do silently. The ufw rule is only offered for removal and never removed without asking; and on Wayland the extension stays loaded until you log out and back in. Your clone of the repository is left alone — delete it yourself when you are done with it.

To take the firewall rule out by hand:

sudo ufw delete allow 8765:8775/tcp

How many devices

There is no device cap anywhere in the code. What actually bounds it:

No fixed limit
One capture, one H.264 encode, fanned out by multisocketsink. A second television costs network bandwidth, not another encoder.
Practical ceiling
11
The default stream port range is 8765–8775. Widen it in the preferences if you genuinely need more.
Bandwidth each
~6000 kbps
The default bitrate at 1080p, per receiver, over your Wi-Fi uplink. Lower resolutions use less.
Reconnect attempts
3
Per receiver. Each one runs on its own thread, so one unreachable television marks only its own session failed and the others keep playing.
Exercised with
3
Three receivers in the hardware checklist, including adding a third mid-stream with no new portal prompt and no interruption.
Real hardware tested
1
A single “Smart TV” Default Media Receiver — and the stream format is not yet confirmed on it.

If something goes wrong

Start here. It checks everything the helper depends on and names what is missing:

~/.local/share/cast-display/cast-helper/venv/bin/python -m cast_helper --doctor

It reports on the session, GStreamer and which encoder it chose, a real ten-frame encode, ffmpeg, the ScreenCast portal and its source types, Network Displays, every network interface, the cast libraries, and the devices it can see in five seconds. Privacy and ports

The stream is your screen, so it is treated as one.

  • The URL contains a 128-bit random token. Without it you get 404.
  • Only the receivers you cast to may fetch it. Any other address gets 403, even with the correct token.
  • The server binds a fixed port range (8765–8775 by default) so you can firewall it deliberately, rather than a random high port that cannot be allowed in advance.
  • The URL uses the network interface that reaches that particular receiver, not whichever one happens to route to the internet. This matters with a VPN, Docker or several NICs.
  • No telemetry, no account, no cloud service. The only outbound connections are mDNS discovery on your LAN and the Cast protocol to the receivers you chose.
  • The screen-share permission is stored in ~/.local/state/cast-display/portal.json so you are not asked every time. The uninstaller deletes it.

5353UDPin/out, LANmDNS discovery of receivers
8765–8775TCPinbound from receiversThe stream itself. Configurable.

How it works

Two processes. A GNOME Shell extension owns the user interface and the monitor layout; a Python helper owns the capture, the encode and the receivers. They speak D-Bus (org.cast.tools.Cast1, API v2).

The Shell is single-threaded and shared with the whole desktop and a stall in an extension stalls the session. Capture, H.264 encoding, mDNS discovery and talking to televisions all block or go wrong slowly, so they live in a separate process that systemd can restart without touching the Shell. The helper also outlives the extension's disable(), which is what makes a cast survive a screen lock. The Shell's copy of the state is a view; the helper is the truth.

One capture is encoded once and fanned out to every receiver by multisocketsink, with the muxer's stream header replayed and keyframe-aligned joins, so a late receiver gets a decodable copy rather than a slice of someone else's.

What it costs

Measured on the reference machine through the full pipeline, software encode, one receiver:

EncodeCPUMemoryFirst frameLag behind live
720p30, x264enc veryfast/zerolatency61%~100 MB0.42 s0.13 s
1080p30, x264enc veryfast/zerolatency114–132%~135 MB0.24 s1.20 s

One core is 100%. Because 1080p software encode costs more than a full core, the helper defaults to 720p when there is no hardware encoder and to 1080p when there is. Add the receiver's own buffering on top of those latencies.

Development

Neither a television nor a second monitor is needed. The harness replaces both and a fake receiver is not a stub: “playing” runs ffprobe against the stream URL and fails unless a video stream actually decodes. 

make test                                 # everything CI runs

cd helpers/cast-helper
./dev/run_helper.sh --testsrc --fake 2    # no screen, no portal, no TV
./dev/run_nested_shell.sh                 # the extension in a real Shell
./dev/run_nested_shell.sh --devkit        # ...one you can click in
./dev/measure_stream.sh 1280x720@30       # CPU, latency, time to first frame
./dev/spike_formats.py --local            # serve each format and decode it

CI runs three jobs: the helper (ruff, then pytest under dbus-run-session), the extension (eslint, node --test and a strict schema compile) and packaging, which builds both the extension zip and the release tarball and asserts that the Python helper has not leaked into the zip.

Further reading lives in the repository, under docs/: the architecture, how the stream format was established, the exact caps that make a virtual monitor usable, the hardware checklist and the defects this rewrite fixed — each reproduced by measurement first.
